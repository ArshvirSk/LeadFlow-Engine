## Story AUTH-S01: Core Authentication Infrastructure

_As a freelancer, I can securely log in and access only my own leads and profile data._

### AUTH-T01 — Integrate Clerk SDK

- **ID:** AUTH-T01
- **Phase:** 1
- **Dependencies:** INFRA-T01
- **Estimate:** 3 SP
- **Owner:** Backend / Full-stack
- **Acceptance Criteria:**
  1. Users can sign up and log in via Clerk (email + Google OAuth at minimum)
  2. Clerk JWT issued on login and verifiable by the Fastify API
  3. `userId` extracted from JWT and available in all request handlers as `req.userId`
  4. Frontend redirects unauthenticated users to `/sign-in`

#### Subtasks:

- Install `@clerk/clerk-sdk-node` in `packages/api`
- Install `@clerk/clerk-react` in `packages/web`
- Configure Clerk publishable key and secret key as environment variables
- Create Clerk JWT template that includes `userId` in claims
- Set up `ClerkExpressRequireAuth` middleware equivalent for Fastify
- Wrap all protected Fastify routes with Clerk auth middleware
- Configure React Router with `<ClerkProvider>` and `<SignedIn>` / `<SignedOut>` guards
- Set up `/sign-in` and `/sign-up` routes using Clerk components

### AUTH-T02 — JWT Middleware for Fastify

- **ID:** AUTH-T02
- **Phase:** 1
- **Dependencies:** AUTH-T01
- **Estimate:** 2 SP
- **Owner:** Backend
- **Acceptance Criteria:**
  1. All protected endpoints return `401 Unauthorized` without a valid Bearer token
  2. Expired tokens return `401` with `{ error: 'token_expired' }` message
  3. `req.userId` is set and typed on every authenticated request
  4. Auth middleware adds < 5ms overhead to p99 request latency

#### Subtasks:

- Create `authenticate` Fastify plugin in `packages/api/src/middleware/auth.ts`
- Implement JWT verification using Clerk's JWKS endpoint
- Add JWKS public key caching with 1-hour TTL
- Extend Fastify request type to include `userId: string`
- Register middleware on all routes under `/api/*` prefix
- Write tests: valid token passes, invalid token returns 401, expired token returns 401

### AUTH-T03 — API Key Issuance for Browser Extension

- **ID:** AUTH-T03
- **Phase:** 3
- **Dependencies:** AUTH-T02
- **Estimate:** 2 SP
- **Owner:** Backend
- **Acceptance Criteria:**
  1. Users can generate a personal API key from profile settings
  2. API key stored as hashed value in database (never stored in plaintext)
  3. Extension capture endpoint (`POST /api/leads/capture`) validates API key + origin
  4. API keys can be revoked and regenerated by the user

#### Subtasks:

- Create `api_keys` table: `(id, user_id, key_hash, created_at, last_used_at, revoked_at)`
- Implement `POST /api/profile/api-key` endpoint: generates 32-byte random key, hashes with SHA-256, returns plaintext once
- Implement API key validation middleware for extension endpoint
- Add origin validation (check `Origin` header against allowed extension origins)
- Implement `DELETE /api/profile/api-key` for revocation
- Add "API Key" section to Profile Settings UI with generate/revoke controls

### AUTH-T04 — Rate Limiting Middleware

- **ID:** AUTH-T04
- **Phase:** 1
- **Dependencies:** AUTH-T02, INFRA-T03
- **Estimate:** 2 SP
- **Owner:** Backend
- **Acceptance Criteria:**
  1. Standard endpoints limited to 100 requests/minute per user (Redis-backed)
  2. LLM-dependent endpoints limited to 10 requests/minute per user
  3. Rate limit exceeded returns `429 Too Many Requests` with `Retry-After` header
  4. Rate limit counters reset on rolling 60-second window

#### Subtasks:

- Install `@fastify/rate-limit` with Redis store
- Configure default rate limit: 100 req/min per `userId`
- Create `strictRateLimit` decorator for LLM endpoints: 10 req/min per `userId`
- Apply `strictRateLimit` to: `POST /api/leads/:id/outreach/regenerate`, `GET /api/leads` (NL query), `POST /api/outreach/send`
- Return `Retry-After` header with seconds until reset
- Write tests: send 101 requests, assert 101st returns 429

## Story AUTH-S02: Advanced Security Features

### AUTH-T05 — Signed HMAC Tokens for Briefing Actions

- **ID:** AUTH-T05
- **Phase:** 3
- **Dependencies:** AUTH-T02
- **Estimate:** 2 SP
- **Owner:** Backend
- **Acceptance Criteria:**
  1. Email briefing action links contain a signed HMAC-SHA256 token
  2. Tokens are single-use (invalidated after first use) with 48-hour expiry
  3. `POST /api/briefing/action` validates token without requiring Clerk login
  4. Invalid, expired, or reused tokens return `401`

#### Subtasks:

- Create `BriefingToken` utility: generates `HMAC-SHA256(userId:leadId:action:timestamp, BRIEFING_SECRET)`
- Store issued token hash in Redis with `userId:leadId:action` key and 48h TTL
- On token validation: verify HMAC signature, check expiry, check Redis for single-use (delete after first use)
- Update `POST /api/briefing/action` to use `validateBriefingToken` middleware
- Generate tokens during FR-13 briefing email generation
- Write tests: valid token passes, expired token fails, reused token fails

### AUTH-T06 — Community OAuth Token Storage

- **ID:** AUTH-T06
- **Phase:** 3
- **Dependencies:** AUTH-T01
- **Estimate:** 3 SP
- **Owner:** Backend / Security
- **Acceptance Criteria:**
  1. Slack, Discord, and Telegram OAuth tokens stored AES-256 encrypted at rest
  2. Tokens never exposed in API responses (write-only — only status and scope shown)
  3. Token rotation handled gracefully (revoke old, store new)
  4. Tokens excluded from all analytics exports and logs

#### Subtasks:

- Implement `CryptoService` using Node.js `crypto` module: AES-256-GCM encrypt/decrypt
- Store `ENCRYPTION_KEY` (32 bytes) as Railway secret (never in code or logs)
- Create `community_tokens` table: `(id, user_id, platform, encrypted_token, iv, scope, created_at, expires_at)`
- Encrypt token before INSERT, decrypt only within server-side workers (never in API responses)
- Implement token status endpoint: returns `{ platform, connected: boolean, scope: string[] }`
- Add token expiry detection and prompt user to reconnect
- Audit all API response serializers to confirm no token fields leak
